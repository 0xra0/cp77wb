# v1.0 verified .NET WolvenKit worker

v1.0 introduces `cp77wb-wkit-worker`, a small .NET 10 sidecar under `extras/cp77wb_wkit_worker`. It references WolvenKit 9.0.1 packages and is the preferred native conversion backend **only after its runtime self-test passes**.

## Why a worker

The v0.9 Python importer can reproduce World Builder's Object Spawner transformation once it has default RED JSON templates, but template capture still depended on WScript and final serialization depended on `convert deserialize`. v1.0 moves both WolvenKit-specific primitives behind one small process boundary while leaving deterministic World Builder transformation logic in Python.

```text
World Builder export
      │
      ├─ cp77wb Python importer
      │        ▲
      │        │ exact RED defaults
      │        │
      │   .NET 10 worker ── WolvenKit.RED4 9.0.1
      │        │
      │        └──────── JSON → CR2W
      ▼
streaming sectors / block / device resources
```

## Build

```bash
cp77wb worker-build
cp77wb worker-build --run
```

The preview reports the exact `dotnet publish` command. The equivalent direct build is:

```bash
./extras/cp77wb_wkit_worker/build.sh
```

The worker source is installed alongside cp77wb by `install.sh`, so this remains available after installation.

## Authoritative self-test

```bash
cp77wb worker-preflight --worker /path/to/cp77wb-wkit-worker
```

The worker loads the installed WolvenKit assemblies and attempts two real operations:

1. instantiate a RED `worldStreamingBlock` and serialize it using WolvenKit's RED JSON machinery;
2. wrap that root as WolvenKit CR2W JSON, deserialize it, write it through the discovered CR2W writer, and verify the resulting file starts with `CR2W`.

cp77wb enables the worker only when both capabilities are true. The JSON protocol is `cp77wb-wkit-worker/1`.

## Direct bundle generation

```bash
cp77wb worker-bundle MyWorld_exported.json ./templates.json \
  --worker /path/to/cp77wb-wkit-worker
```

This is a preview. Add `--run` to create the bundle. The resulting bundle intentionally uses the same `cp77wb-wkit-templates/1` schema as v0.9, so the Python importer has one stable internal format regardless of which backend produced the defaults.

## Direct import

```bash
cp77wb worker-import MyWorld_exported.json ./native-out \
  --worker /path/to/cp77wb-wkit-worker
```

Add `--run` only after preflight/preview succeeds. cp77wb then:

1. asks the worker for the exact required RED defaults;
2. generates WolvenKit JSON with the v0.9 importer mirror;
3. asks the worker to serialize each JSON file to CR2W;
4. independently verifies every expected target and CR2W magic.

## Build workspace

```bash
cp77wb build-worker-import ./build/MyWorld \
  --worker /path/to/cp77wb-wkit-worker

cp77wb build-worker-import ./build/MyWorld \
  --worker /path/to/cp77wb-wkit-worker --run
```

On success `.cp77wb-build.json` records:

```text
lastImportBackend = dotnet-wolvenkit-worker
```

`build-status` must still report `importComplete: true` before packing.

## Fallbacks

v1.0 does not delete older paths. In priority order:

1. verified .NET worker;
2. v0.9 captured template bundle + WolvenKit CLI `convert deserialize`;
3. exact upstream World Builder Object Spawner WScript importer generated by `build-prepare`.

A failed worker self-test is therefore a backend-selection result, not a reason to risk an unverified conversion.

## v1.0.1 diagnostics

See `v101-worker-diagnostics.md` for `worker-inspect`, API-profile fingerprinting, full publish-log capture and `worker-doctor` support bundles. These are specifically intended for a deferred target-machine test.

## Current release-test boundary

The cp77wb build container used for v1.0 does not provide a .NET SDK/runtime, so the bundled worker source cannot be compiled against real WolvenKit packages in that environment. The Python worker protocol, safety gates, build integration, CR2W verification, and failure behavior are covered by contract tests. On a real machine the first required command is `worker-preflight`; cp77wb does not claim the worker backend is authoritative until that real runtime self-test passes.
